Guidance

How to choose a configuration, what belongs in each slot, and the rules that keep cards consistent across surfaces.

Choosing

Picking a Thumbnail Type #

Thumbnail Type is a statement about what the card is about. Choose by asking what the user needs to recognize first.

UseWhenDon't
DominantThe visual is the content — link previews, media shares, hero announcements. The 16:9 banner leads.Don't use for dense lists; one Dominant card per viewport region is plenty.
Primary (img 128)The image matters but shares billing with metadata — file previews with rich detail lines.Don't pair with a Title Thumbnail unless both identities are truly distinct.
Secondary (img 72)Compact scannable rows where the image is a recognition aid — trending files, recent documents.Don't put text inside the media; 72px is a glance target.
NoneIdentity lives in the Title Thumbnail or the content itself — site cards, people cards, activity digests.Don't fake a banner inside Slot Above Divider; switch to Dominant instead.
Choosing

Emphasis & Density #

Emphasis answers "how loud is this card right now": Default for resting content, Active for the selected/highlighted state (brand-tinted fill, accent stroke), Floating for cards lifted above the canvas — pickers, previews, drag states. Emphasis is a state, not a style choice; the same card moves through emphases as the user interacts.

Density answers "how much room does this surface have": Comfy is the default for primary canvases, Compact removes 24px of vertical air for dashboards and side panels, and Cardless strips the chrome entirely for embedding inside an already-carded parent — a card within a card should never draw two borders.

Cardless exists to prevent double chrome. If the parent surface already provides containment (a sheet, a grouped list, another card), use Cardless and let the parent own the border.
Slots

Slot Do's and Don'ts #

Slots are contracts. These rules keep slotted content from breaking the card's rhythm.

Slot Above Divider is for content that describes the card's subject — file grids, activity feeds, galleries. Keep it self-contained: no interactive elements that compete with the footer actions.
Slot Below Divider is for content that acts on the subject — composers, reaction strips, expandable detail. If the divider is hidden, prefer Slot Above Divider; a below-slot without a divider reads as unanchored.
Detail line icons should always be 16px Fluent regular-weight glyphs from fluenticons.co. Never scale a 24px icon down — optical weight goes muddy.
Never place a second card inside a slot with chrome on. Use a Cardless instance, or the purpose-built File Card tiles from the OD library.
Footer

Footer Rules #

Maximum two labeled buttons plus the trailing utility slot. First button is the primary action and may take the filled treatment; the second stays outlined. Three or more actions means the extras belong behind More Horizontal in the overflow. Button labels are verbs — "Open", "Share", "Follow" — never nouns. Icon-only buttons are reserved for the trailing 24×24 slot.

The footer is the only interactive zone in a Static card. If the whole card is tappable, the footer becomes redundant — pick one interaction model per card.

Architecture

The configuration logic — why the Card is three orthogonal axes plus slots, and how the pieces compose without variant explosion.

Model

The Configuration Model #

The Card separates three concerns that would otherwise multiply into hundreds of bespoke components:

Thumbnail Type is the layout axis — it decides the media footprint and therefore the card's internal flow (stacked for Dominant, side-by-side for Primary/Secondary, text-first for None). Emphasis is the state axis — visual loudness, orthogonal to layout. Density is the context axis — how much room the host surface affords, including the degenerate Cardless case where the host owns containment.

Because the axes are orthogonal, 4 × 3 × 3 = 36 combinations are expressible from one component — and exactly one is excluded (None + Floating + Cardless) because a chrome-free, media-free card has no surface left to elevate. The component set publishes 35 variants.

Content never lives on an axis. What the card shows (files, people, activity) is slot payload; how it's arranged (layout, state, context) is axis configuration. Mixing the two is what causes variant explosion in legacy card libraries.

Structure

Container Hierarchy #

Two nested containers give the Card its flexibility:

Primary Container owns the 12px padding and the relationship between Leading Media and everything else. When Thumbnail Type changes, only Primary Container's flex direction changes — column for Dominant (banner above), row for Primary/Secondary (media leading). Nothing inside Secondary Container knows or cares.

Secondary Container owns the text stack: Title Block → Detail Lines → Slot Above Divider. Its rhythm (8px gaps, 4px between detail rows) is constant across every variant, which is why a card re-flows perfectly when you flip axes.

The Divider / Slot Below Divider / Card Footer trio sits outside Primary Container, at the card root. That placement is deliberate: the action zone spans the full card width even when the content zone is split by a leading image.

Slots

Why Slots, Not Props #

Eight regions are slots rather than baked-in content. The reasoning:

A property system (INSTANCE_SWAP with preferred values) can only offer content the library anticipated. Slots invert this — the Card guarantees geometry (position, size bounds, spacing participation) and accepts any content. The File Card grids in the People example and the activity feed in the Site example were never designed into the Card; they compose into Slot Above Divider because the slot only enforces width and rhythm.

Slots are also the hidden-by-default mechanism. Slot Above Divider, Slot Below Divider, Custom Slot, Divider, and Footer all ship hidden. A default Card is title + caption + details — everything else is opt-in. This keeps the property panel honest: enabling a region is a visible, intentional act.

Placeholder promotion: every slot ships with a .placeholders library instance (.Slot Placeholder 295×48, .Image Placeholder 295×144, .Title Thumbnail Placeholder 48×48, .Detail Icon Placeholder 16×16). Placeholders render the diagonal-stripe treatment in specs and are swapped out — never resized — by consumers.
Logic

Visibility & Dependency Logic #

Regions toggle independently, but three dependencies are enforced by convention:

RuleLogic
Divider ⇢ below-contentThe Divider only earns its pixel when something exists on both sides — hide it if neither Slot Below Divider nor Card Footer is on.
Footer ⇢ overflowThe trailing 24×24 slot renders whenever the footer does; swap its content rather than hiding it, so footer geometry stays stable.
Detail Lines ⇢ rowsDetail Lines is a single toggle for the two-row block. Single-row cards hide row 2's content, not the block — keeping the 36px reservation avoids reflow on data change.
Pipeline

Compile Mapping #

How the configuration model lands in the Monocore build pipeline:

Slots become SLOT component properties bound via componentPropertyReferences.slotContentId; regions that pair a slot with a visibility toggle (Slot Above/Below Divider) receive both bindings in a single componentPropertyReferences write — two separate writes would overwrite the first key (R27). Footer button icons ride on isExposedInstance (R25), because the Plugin API blocks property references on instance sublayers (R12). Text properties (Title, Caption, Detail 1/2, Label) bind through characters references after style assignment (R2, R5).

The full 14-phase build and gate table lives in the internal Cold Start Pipeline runbook.

Leading icons

Icon roles follow the state's foreground token, not the Text token. The pairing is per-state:

Behavior #

Pill shape, always. The 999 corner radius isn't a token alias — it's literal. The badge intentionally bypasses the Monocore corner-radius ladder so that growth in either axis always produces a half-pill.
Interactive vs Static signals tappability through color alone. The two share the same surface (RaisedSecondary) and stroke (Container) but diverge on foreground: Static is Text/Secondary (neutral grey), Rest is Text/Interactive (brand). Use Interactive only when the badge opens a menu, filters a list, or otherwise responds to taps — the brand color is a tap-target promise.
Active is interactive-only. There is no Static Active variant. If you need a "selected" indicator on a Static badge, swap the surface manually or use a separate component — do not retire the semantic meaning of Active by using it for static decoration.
No trailing icon. Interactive Rest and Static variants at Default size share identical widths (71dp with Avatar/Icon) — confirming no trailing affordance glyph exists in the set. If a dismiss or chevron affordance is needed, it must come from context (e.g. a filter row pattern), not from the Badge itself.

Rules & workflow Accessibility
Rules

Behavioral Rules #

Five rules govern how the system behaves. Each one closes off a class of mistake the design system has historically made: arbitrary elevation steps, ad-hoc semantics per component, and value drift when context changes.

Semantic stability. A semantic role's meaning never changes. Surface/Floating always means "floating temporary UI surface" — only its tonal value shifts between L1 and L2.
Primary means "always extreme," not "always lighter." Unlike Surface/Canvas, which adapts to its container, Surface/Primary always holds the extreme value (pure white in light, pure black in dark) regardless of elevation. On a Base or Raised container it reads as lifted (lighter in dark mode). But inside a dark Overlay (Grey/10), a Primary card goes to Grey/0 — darker than its container, an intentional inversion. Use it for cards and contained regions that must maintain maximum contrast against their surround rather than blending into the elevation hierarchy.
No new elevations. The system has L1 and L2, and only L1 and L2. Floating is its own thing, not L3.
Floating is not elevation. Menus, popovers, tooltips, and reaction pickers use Surface/Floating regardless of whether they appear in an L1 or L2 parent context. They are transient, not canvas-elevated.
Platform-chrome surfaces are exceptions. Surface/Dominant (top) and Surface/Quaternary (bottom tabs) exist outside the canonical L1/L2 system to give the OS room to impose its own materials. Their declared values are fallbacks — actual rendering may be overridden by iOS 26 large-title materials or Android tab-bar blur on supported devices.
Overlay forces L2. Presenting a modal, sheet, or drawer shifts the parent frame from L1 to L2. This means the apparent Dark L1 value collision between Surface/Overlay and Surface/RaisedSecondary (both resolve to Grey/10) is never actually rendered — by the time Surface/Overlay is on screen, the surrounding tokens have already resolved to their L2 values, where RaisedSecondary becomes Grey/14 and the visual separation returns.
A handful of tokens differ between L1 and L2. The rest resolve to the same value across environment levels. The L1/L2 distinction matters most for: Floating, Sunken, Interactive. (Base and RaisedSecondary share a single value across both L1 and L2 — the environment shift no longer applies to them.)
Workflow

How Designers Use It #

The system reduces every surface decision to two choices: pick the role, set the parent's mode. Everything else resolves automatically.

  1. Pick the semantic role that describes intent (Surface/RaisedBase, Surface/Floating, etc.).
  2. Bind the variable to a fill or stroke.
  3. Set the parent frame's mode (Light L1, Light L2, Dark L1, Dark L2).
  4. The variable resolves to the correct tonal value automatically.

When entering an elevated context (sheet, modal, drawer), the parent frame's mode switches from L1 to L2 — every surface inside picks up the L2 tonal values without changing token names.

Accessibility — WCAG AA Contrast #

Translucent surfaces (Subtle, Glass, Scrim) must be composited over a known canvas before testing — results below assume an opaque host.

The Token Table above shows two columns of new dark-mode raised values (Surface/Floating at Grey/22–24, RaisedPrimary at Grey/24) sitting closer to the canvas tier than to the IC variants.   1. Promote Text/Primary as the default body text everywhere. Reserve Text/Secondary for ≥14pt or non-body roles (timestamps, captions, helper labels). The current Secondary value is calibrated for legibility on Canvas, not on every raised tier.
  2. Treat Text/Interactive as a large-text or UI-component role. It works for buttons and tappable labels; for inline body links, fall back to Text/Primary with an underline.
  3. Document the IC modes as the AA-Normal-everywhere variants. When a screen has an accessibility-critical context (forms, financial data, settings), authoring against an IC mode guarantees the full text ramp passes 4.5:1 against every surface.

Why three ramps #

Most spacing decisions are about gaps — how far one element sits from the next. That's the Size ramp. But two other situations come up often enough to deserve their own scales: micro-adjustments to optically align content against a container that has forced padding (Nudge), and the case where Figma's one-variable-per-property limit forces a designer to pre-compute the sum of a Size and a Nudge as a single named token (Combined).

Spacing vs Nudge. Use Size/* for gaps between elements — this is most spacing. Use Size/Nudge/* for optical adjustments inside or against a component that has forced padding (an icon, a ghost button) where the standard ramp would over- or under-correct. If you're nudging anything that isn't an icon or ghost-padded container, you probably want a Spacing token instead.

Swapping the active palette #

A product can ship multiple brand palettes (e.g. Teams default, partner co-brand, seasonal palette) and swap the active one at runtime. The Accent tokens never change; the palette they alias to does.

  1. Define palettes in the Brand collection. Each palette is a complete set of Brand light/* and Brand dark/* primitives.
  2. Bind components to Brand/Accent *. Components never reference the palette directly.

  4. Add new palettes by extending the Brand collection. The Accent ladder doesn't change shape.

How theming works #

The Accent ladder describes the role of a branded surface or fill — "most prominent," "standard," "subtle," and so on — without committing to a specific color. The active brand palette (set by the product) supplies the underlying hex values. Accent tokens are mode-aware in the same sense as the Surface ladder. Scaling Rules

A two-part framework for Dynamic Type. First, classify each component into a scale tier that sets how much its text is allowed to grow (Scale0, Scale1, ScaleMax). Then, at the upper bound of that tier, use reflow tokens to decide what happens to elements that still won't fit — extending vertically (extend0–extendFit) or stacking columns (virticalStack).

3 scale tiers 5 reflow tokens iOS & Android
Foundations

Scale tiers #

Each component belongs to one of three tiers based on how much its text is allowed to grow. The tier sets the ceiling; the reflow tokens decide what happens at that ceiling.

TierMaximum scaleUse it for
Scale01× · no scaleComponents whose text content is always the same and lives in the same location. Tab bars, fixed labels in chrome that the user reads at a glance, content anchored to a UI region rather than to body text.
Scale11.3× · capped scalingComponents whose text lives in the same location and doesn't change often. Headers, search placeholders, badges, token fields, message-compose chrome — text that's allowed to grow somewhat while the surrounding container stays usable.
ScaleMaxUnrestrictedComponents whose text is the user's content — chat list items, message bodies, anything the user reads attentively. Scale continues to the full Dynamic Type ceiling; reflow tokens take over from there.
Pick the tier from the role, not the size. The question is "what does this text do?" — chrome (Scale0), navigation or container labels (Scale1), user content (ScaleMax) — not "how big do I want it to be."
Reflow

Reflow tokens — extending lines #

At the upper bound of Scale1 and ScaleMax — the max zoom level where comprehension is already constrained — four extend tokens control how many additional lines a text element is allowed to wrap to before truncating. Assign the token per text element; the cell as a whole inherits the most permissive value of its children.

TokenValueBehavior
extend0Plus 0No lines added. The text truncates at its original line count.
extend1Plus 1Add one more line before truncating.
extend2Plus 2Add two more lines before truncating.
extendFitUnboundNever truncate. Let all text reflow into as many lines as it needs.
Pick the smallest extend that preserves the message. A timestamp doesn't need extendFit; a primary message label might. Defaulting every element to extendFit defeats the framework — every cell takes unbounded vertical space and pushes the next cell off-screen.
Reflow

Reflow tokens — stacking columns #

When the extend tokens still aren't enough — typically because the leading column has grown so wide it begins to clip the trailing column — the trailing column reflows beneath the leading column instead of competing with it for horizontal space.

TokenBehavior
virticalStack (sic — token name as published)When the leading column begins to clip the trailing column, reflow the trailing column under the leading column.

This gives each cell two degrees of freedom at max zoom: vertical expansion within the original row (the extend tokens), and column-stacking once horizontal space is exhausted (virticalStack). Together they let a chat row with a long message and a long timestamp degrade gracefully instead of overlapping.

The order of fallback. The extend tokens are tried first — they preserve the two-column layout. virticalStack is the second step, only reached when the trailing column still can't fit. Two cascading fallbacks, applied in sequence by the framework.
Platform implementation

iOS implementation #

iOS doesn't use a decimal scaling factor. Each component opts into one of four UIContentSizeCategory strategies that govern the band of allowed text sizes under the user's Dynamic Type setting. The framework tiers (Scale0, Scale1, ScaleMax) map onto these strategies as follows.

The four iOS strategies

Each strategy defines a min and max content size category. Sizes outside the band are clamped to the bound. The five accessibility categories (AX1–AX5) are only reachable when the user enables Larger Accessibility Sizes in iOS Settings > Accessibility > Display & Text Size.

iOS strategy Range What it does
default xSmall → AX5 Follows the user's device setting with no upper bound. Text scales through every category including all five accessibility sizes.
large xSmall → Large Min is unbounded; max preferred size is Large (the system default). Components grow from the smallest scale up to Large and stop.
excludeAccessibilityCategory xSmall → xxxLarge Caps at xxxLarge — the largest non-accessibility size. AX1–AX5 never reshape the layout.
largeToExcludeAccessibilityCategory Large → xxxLarge Floored at Large, capped at xxxLarge. Text never goes below the system default and never enters the accessibility range.

Mapping scale tiers to iOS strategies

The Android scaleX ladder and iOS UIContentSizeCategory strategies meet at the same intent for each tier.

Scale tier Android iOS strategy Why they match

Scale0 Decimal cap = 1.0× (fixed) excludeAccessibilityCategory iOS has no true "freeze" strategy in the four named ones; excludeAccessibilityCategory is the closest match because the AX categories never reshape the layout. For genuinely fixed chrome (e.g. tab-bar labels that must never change size), use a non-UIFontMetrics-scaled font instead.

Header rule. When a Header is implemented on iOS, prefer largeToExcludeAccessibilityCategory over plain large. The floor keeps the title from shrinking below the device default when the user's preferred size is below Large, which preserves the visual hierarchy headers depend on. TilesGrid and other layout-sensitive surfaces use excludeAccessibilityCategory for the same reason — the AX range would break the grid.

Applying the framework #

Two decisions per component — the tier and the per-element reflow tokens. Everything in between is interpolated.

  1. Pick the tier for the component as a whole. Is it chrome (Scale0), navigation/container (Scale1), or user content (ScaleMax)?
  2. For Scale1 and ScaleMax, assign an extend token to each text element based on how much of it must remain readable at the cap.
  3. Assign virticalStack to the trailing column if it still clips after the extends are applied.
  4. The framework handles the rest. Intermediate sizes interpolate between the default layout and the cap layout you've configured. No per-step authoring required.

Why a scaling framework #

Dynamic Type lets users push text to extreme sizes for accessibility. Without intervention, every text element scales freely — and components collapse: timestamps collide with labels, tab labels wrap to three lines, search placeholders shove their icons off-screen. The framework gives designers two levers — a per-component scale tier and per-element reflow tokens — so a chat row can stay legible at max zoom without breaking the rest of the screen.

Tune at the cap, not at every step. Designers configure behavior at one point — the upper bound of the component's scale tier. The framework interpolates every intermediate Dynamic Type size between the default layout and the configured max-zoom layout.

Method #

Same chip thresholds for both columns. Accessibility — Stroke

Architecture

How to read this

Method #

For each stroke role, the matrix below shows its contrast ratio against every opaque surface in each of the four primary modes. Cells are chipped against the 3:1 non-text-contrast threshold.

3.0+ Meets WCAG 1.4.11 <3.0 Below threshold

Not every stroke needs 3:1. WCAG 1.4.11 applies to graphical elements that convey information — component boundaries that distinguish an interactive control from its background, focus rings, form-field outlines, etc. It does not apply to decorative separation. The Monocore stroke system has three tiers:
  • Stroke/Accessible — the AA-grade stroke. Used for focus rings, form field borders, and any boundary that must convey UI state. Required to meet 3:1 on every surface it can land on.
  • Stroke/Container (outer), Stroke/ContainerRaised — container edges. They define where a card or grouped region begins, but the contrast is also doing layout work, not state communication. Authoring with a target of 3:1 where reachable is preferred but not strictly required. Often paired with elevation or fill differentiation to reinforce boundaries.
  • Stroke/Divider, Stroke/Elevated (outside), Stroke/onMedia (outer) — decorative. Row dividers, hairline separators, and floating-surface edges that don't carry state information. Intentionally below 3:1 so they read as quiet visual organization. Not required to meet WCAG 1.4.11.
How to use this page. Look at the Stroke/Accessible matrix first — it should be all green; any red there is a real bug. For the other roles, red cells are expected; the matrix exists so designers can predict how a stroke will read against a specific surface, not to flag failures.

Overlay surfaces and the Modal extension #

The Modal extension exists because content rendered inside an Overlay needs different values than content on the base canvas. The rule below explains why — and what breaks if a modal frame is left bound to Theme instead of Modal.

Overlay surfaces in dark mode are the L2 canvas. Modal/sheet content must be set to L2 mode.

Set the frame mode to Dark L2 for any content nested inside an Surface/Overlay, Surface/Floating, or other temporary elevated surface. If you leave it on Dark L1, surfaces that should lift above the overlay will instead match it — in the worst case, the card becomes mathematically identical to its background and vanishes.

Frame mode: Dark L1 wrong Container vs Overlay: 1.00:1
Stack: Canvas #000000 → Overlay #1a1a1a → Container #1a1a1a
Frame mode: Dark L2 correct Container vs Overlay: 1.06:1 · 2 Grey steps
Stack: Canvas #1a1a1a → Overlay #1a1a1a → Container #1f1f1f
  • The architectural contract. Surface/Overlay in Dark resolves to #1a1a1a (Grey/10) — which is also Surface/Canvas in Dark L2. Overlay is the L2 canvas at the surface layer. Setting the inside-overlay frame to L2 makes every nested role re-resolve correctly against that elevated canvas.
  • Symptoms if you forget. Surface/RaisedBase and Surface/RaisedSecondary drop from 1.66:1 to 1.38:1 against the Overlay (17% less lift). Surface/Group/Primary/Base becomes mathematically identical to the Overlay (1.00:1) and disappears entirely.
  • What gets fixed by L2. Canvas L2 = Overlay (no visible delta needed at that layer). Containers/Primary/Base steps Grey/10 → Grey/12. RaisedSecondary stays Grey/20 but the perceptual delta to the now-matching Overlay/Canvas pair is consistent. The hierarchy holds.
  • Light mode is fine. Canvas and Overlay are both #ffffff in both light tiers, so the relationships hold mathematically without needing an L2 mode shift. Card delineation against a white overlay relies on stroke + shadow (the same way it does on the white canvas), not on a tonal step.

Stroke/Container (outer) preserves badge silhouettes when fill matches the container surface.

The real iOS Badge component fills its pill with Surface/RaisedSecondary and outlines it with Stroke/Container (outer). When that badge sits inside Surface/Group/Primary/Container — the standard iOS list cell — the badge fill resolves to the same hex as the container surface in both light and dark. Without the stroke, the pill has zero tonal lift and disappears.

Badge fill alone no stroke Fill 1.00:1 against Container
Stack: Canvas #1a1a1a → Overlay #1a1a1a → Container #333333 → Badge fill #333333 (no boundary)
Badge fill + Stroke/Container (outer) correct Edge ratio 1.51:1 — silhouette holds
Stack: Canvas #1a1a1a → Overlay #1a1a1a → Container #333333 → Badge fill #333333 + stroke #4d4d4d
  • Same hex on both sides. Surface/RaisedSecondary and Surface/Group/Primary/Container resolve to #f0f0f0 in light themes and #333333 in dark. A badge filled with one inside the other has 1.00:1 contrast at the fill layer in both modes. Without an edge token, the pill silhouette doesn't exist.
  • What Stroke/Container (outer) contributes. Grey/76 (#c2c2c2) in light, Grey/30 (#4d4d4d) in dark — both clear the WCAG 1.4.11 3:1 threshold against every standard container surface. On the badge specifically, the 1px stroke draws the boundary the matching fill can't.
  • Where the badge actually uses it. The Static and Interactive Badge variants in CXD-iOS bind their container stroke to Stroke/Container (outer) by default (with Stroke/Default as the previous behaviour migrated away from). Concept

Two collections, one extension relationship #

The old system expressed elevation as an L1/L2 mode inside a single Color collection — every variable carried four mode values (Light L1, Dark L1, Light L2, Dark L2). That's been replaced with a two-collection model: Theme (Light - dark) holds the base values with just Light and Dark modes; Modal (Light - dark) is a formal Figma extension (created via the "Extend collection" action in the Variables panel) that inherits every variable from Theme and only stores overrides for the 30 tokens that need to shift in an elevated context.

Modal overrides Theme — it doesn't duplicate it. When you bind a frame to Modal, every token that isn't explicitly overridden falls through to its Theme value, so brand refreshes, primitive swaps, and general theme changes cascade automatically. Only the 30 elevated overrides are stored in Modal; the other 217 variables are pure inheritance.

Below, each category lists only the roles that are overridden in Modal. For every overridden role, the swatches show Theme's base value alongside Modal's override, so the elevation delta is obvious. A short rationale explains what perceptual relationship the override is preserving.

Reading the swatch rows. Each role shows swatches for the Theme (Light and Dark) base values and the Modal (Light and Dark) overrides. The theme-side swatches represent the app default; the modal-side represent what renders inside a sheet, drawer, popover, or modal flow that has been bound to the Modal extension.

Accessibility #

The published component carries a documentation link to the Teams Mobile A11y guidance; the notes below are the parts that bind at spec time.

Button Component

Architecture

Why Monocore ships two button components instead of one, what each axis is actually responsible for, and the exact layer tree behind both.

Model

The Configuration Model #

The Button separates three concerns, and deliberately refuses to absorb a fourth.

Style is the emphasis axis — how loudly the action asks to be taken. Size is the density axis — how much room the host surface affords. State is the interaction axis — Rest, Pressed, Disabled. All three are orthogonal, so 3 × 3 × 3 = 27 variants publish with no exclusions: there is no combination of emphasis, density and interaction that is meaningless.

The fourth concern — width behaviour — is what Button Full-width exists to hold. It could have been a boolean on the main set, and that is the tempting design; it was split out because full-width buttons only ever occur at Large, and folding them in would have published 27 unreachable Medium and Small full-width variants to gain one property.

Width is a container decision, not a button decision. The standard Button hugs its label at every size. Anything that needs to fill its container is a different component with different responsive rules — portrait fills the width inside 16dp padding, landscape and tablet cap at 340dp.

How Size Is Expressed #

Size does not scale the button — it re-selects four independent values.

Height is set explicitly on Content (52 / 40 / 28) with vertical padding pinned at 0, so the row centres its children rather than growing from them. Note the pattern: Large and Medium are the same button at two heights — identical gap, icon box and type style, differing only in height and horizontal padding. Small is the real break, dropping to a 16dp icon box and the Button 2 ramp. If you are implementing a size scale in code, model it as two tiers with a height variable, not three arbitrary sets.

Accessibility #

  • Never put an action in a call out. The component has no interactive slot and no dismiss control — anything essential inside it is unreachable by keyboard or switch control. It is for hints, not decisions.
  • Announce it when it appears. A call out that fades in unannounced is invisible to a screen reader user. Tie it to its anchor and announce it politely on show.

Architecture

Why an eight-value axis is the right shape for a tooltip, what the component deliberately refuses to own, and where the published set drifts.

Model

The Configuration Model #

One axis, eight values, and a hard boundary around what the component will not do.

Tip location is the only property. It sets two things at once: which edge the tail emerges from, and how the body aligns against that tail. Those two are inseparable — a tip on the bottom-left edge only makes sense with the body's left edge aligned to it — which is why they are one variant rather than two axes that could be combined into nonsense.

What the component does not own is placement. It has no anchor reference, no offset property and no collision behaviour. It is a shape that points in a direction; deciding which direction, and where on screen to put it, is the host's job. That is a deliberate split: anchoring depends on scroll position, safe areas and keyboard state, none of which a Figma variant can model.

Choosing the variant is the flip logic. When a call out would run off the top of the screen, the host doesn't ask the component to adapt — it swaps Bottom center for Top center. The eight variants exist precisely so that flipping is a variant change and never a layout hack.

Content

One Slot, and Why #

The Container has a bound text property and nothing else — no icon slot, no action slot, no close button.

That is a scope decision, not an oversight. A tooltip with a button becomes a coach mark, which needs focus management, a dismissal contract and a way to be re-summoned. Adding an action slot here would let any surface create an unreachable control inside a transient popup. The 8dp internal gap hints that a second child was once anticipated; today it never has one.

If you need an action, you need a different component. Do not slot a Button into a Call Out instance. Raise the need for a coach-mark component instead — the accessibility contract is genuinely different.

One shell, six interiors, and a family that has outgrown its name. What Layout actually switches, why the grid is sparse, and what needs consolidating.

Model

The Configuration Model #

Chiclet is the one component in this set where the variant axis changes structure, not just style.

Button varies colour and size. Divider varies an inset. Chiclet's Layout axis swaps the entire interior: Base is an icon-text-chevron row, Reply prepends a quote bar and an attribution glyph, File Chiclet leads with a filetype icon and trails a pair of actions, Video is a media plate with a centred play control and no text at all. Only the shell — 265dp wide, 16dp radius, Surface/Primary, a one-pixel border — survives across all seven.

That is defensible because the thing a chiclet represents is what changes, and the representation dictates the anatomy. It is also why the axis cannot be decomposed: there is no meaningful “Reply + File”.

The shell is the contract, not the interior. Anything consuming a chiclet can rely on the 265dp width, the 16dp radius and the border treatment. Nothing else is stable across layouts — so never write host code that reaches into a chiclet expecting a particular child.
Model

Why the Grid Is Sparse #

Six layouts × two Image values would be twelve variants. Seven are published, and the five gaps split into two different reasons.

Four gaps are meaningless combinations. Base, Base + actions, Reply and Forward have no media plate to switch on, so Image=True would render identically to False. Publishing them would be four variants of pure noise.

One gap is a missing state. Video / Image=False is absent because a video chiclet with no thumbnail has nothing to show — but that is exactly the state a real client hits while the thumbnail is still loading or has failed. Today there is no published answer for it.

Meanwhile Reply and Forward do carry media, through a separate boolean that reveals a 40×40 thumbnail. Two mechanisms for the same idea, on the same component, is the structural problem underneath the naming collision.

Unify the two media mechanisms before adding anything else. Either the Image axis covers every layout that can show media, or media is always a boolean-revealed slot. Keeping both guarantees the next contributor picks the wrong one.

Accessibility

Accessibility #

  • A plain Divider is decorative. It carries no information a screen reader needs; expose it as decorative rather than as a separator with a role, so it does not add noise to a long list.
  • Section Divider is not decorative. Its centre content — a label like “Unread”, or a button — is real content and must be reachable. Do not hide the whole component.
  • The rule fails text contrast by design. Stroke/Divider (#e0e0e0) against a white surface is a non-text boundary, which is permitted — but it means a divider can never be the only cue that two things are different. Grouping, spacing and headings carry the meaning.
  • Do not scale the rule with text size. At 0.5dp the divider is already at the edge of visibility on low-density displays; it should hold its weight while type grows around it.

Divider Component

Architecture

Why the simplest component in the system still has a variant axis, and why Section Divider is built out of Divider rather than beside it.

Model

The Configuration Model #

A rule needs no configuration. An inset rule does — and that is the entire axis.

The Divider publishes one property, Padding, with five values. Four of them shift where the rule starts or stops; the fifth is None. Nothing else varies: weight, colour and height are fixed across every variant. That makes Divider the one component in Monocore where the variant axis is purely spatial.

The reason the inset lives on the component rather than the host is alignment. In a list with 16dp leading content, the rule has to start where the text starts, not where the row starts — otherwise it reads as a boundary around the avatar rather than between two rows. Putting that inset in the component means the value travels with the design system instead of being re-derived in every list.

Zero height is the contract. The Divider box is 0dp tall with the rule drawn on its top edge, so dropping one into an auto-layout stack changes nothing about the stack's rhythm. Every gap you see around a divider belongs to the host. A component that reserved its own vertical space would make list spacing depend on whether a divider happened to be present.

Section Divider consumes Divider, it does not re-draw it. The horizontal variant nests two real Divider instances, each set to fill the space left over by the centre element. That is why a change to the divider colour propagates to section breaks for free — and why the vertical variant, which does not use Divider, is the one that drifts.
Naming

Leading, Trailing, and What They Mean Here #

The variant names describe the edge that gets the inset, not the edge the rule reaches.

16-leading applies 16dp of padding on the leading edge, so the rule begins 16dp in and still runs to the far edge. 16-trailing does the mirror. Read literally the names are unambiguous, but they are easy to misread as “the rule leads by 16” — which would be the opposite. When implementing, map them to a directional inset (padding-inline-start / padding-inline-end) rather than to a physical left/right, so the component keeps working under RTL.

RTL is not handled by the component. The padding is authored as a physical inset in Figma. In code it must become logical, or every inset divider will point the wrong way in Arabic and Hebrew layouts.

Horizontal publishes all three Semantic values — 3 × 3 × 2 = 18. Vertical publishes only Primary and Secondary — 2 × 3 × 2 = 12. The Pill bar has a Semantic axis alone, with Primary and Secondary.

When to Use It #

Horizontal filter buttons sit in a scrolling row above a list. The vertical form — taller than it is wide, at 61 × 51 — stacks a glyph over a label and belongs in a grid rather than a row. The Pill bar is the segmented container that holds a fixed, mutually-exclusive set.

For a single removable selection rather than a filter toggle, use Chip — it is the same size class and is frequently confused with the horizontal filter button.

Active is not the same as Pressed. Active describes whether the filter is applied; State describes what the finger is doing. Both axes are published on both filter buttons, and conflating them is the most likely implementation error in this family.
